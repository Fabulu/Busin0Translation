## 5. Root Cause Analysis: v2 Pipeline FFFF Bug (Tavern Softlock)

### Summary of Bugs

The v2 pipeline (build_full_english_v2.py) has THREE bugs affecting R39:

#### Bug 1: Wrong Offset Base
The pipeline computes offsets relative to payload start (byte 16),
but R39 offsets are relative to the offset table start (byte 240).
This means every injected offset is wrong by 224 bytes (240 - 16).

Specifically, line 392:
```python
payload_rel_offsets = [glyph_stream_base + goff for goff in new_ffff_positions]
```
produces offsets relative to byte 16, but the game reads them relative to byte 240.

#### Bug 2: Lost Mid-Group OT Entries (Not applicable to R39)
R39 has 0 OT entries pointing to mid-group positions (1:1 OT-to-group mapping).
This bug affects other type-15 resources where multiple OT entries share one FFFF group.
For R39 specifically, the pipeline correctly produces 97 groups = 97 OT entries.

#### Bug 3: Glyph Stream Truncation at payload_end
The pipeline uses payload_end (byte 2478) as the stream boundary,
but R39's glyph stream extends to byte 2702.
The last 6 FFFF groups (containing 
OT entries 91, 92, 93, 94, 95, 96)
are in this extended region and would be ignored/corrupted.

### Why This Causes the Tavern Softlock
The game uses the offset table to look up menu/equipment text by index.
When the offset table has wrong values, the game reads garbage data as text,
which can include control codes that cause infinite loops or null pointer
dereferences in the text rendering engine.

## 6. Recommended Injection Strategy

### Option A: In-Place Fixed-Length Replacement (Safest)
```
For each FFFF group:
  1. Calculate original byte length
  2. Encode English translation
  3. If English <= original length: pad with 0x0000 (space)
  4. If English > original length: truncate or abbreviate
  5. Write at exact same position
  6. NO offset table changes needed
```
Pros: Zero risk of offset corruption
Cons: Limited by Japanese text length (but JP chars are 1 glyph each)

### Option B: Delta-Tracking Offset Recalculation
```
1. Record original position of every OT entry (abs = 240 + offset_value)
2. For each entry, note: which FFFF group, byte offset within group
3. Replace desired FFFF groups with new content
4. Track cumulative byte delta from group replacements
5. For each OT entry:
   - new_abs = original_group_new_start + within_offset
   - new_ot_value = new_abs - 240
6. If a replaced group has mid-group OT refs, SKIP that group
   or recalculate within_offset based on translation structure
7. Rebuild OT with ORIGINAL msg_count (97)
8. Assemble: sub-header + seq_data + new_OT + new_stream
9. Update payload_size (must cover at least the main stream)
10. Preserve any data beyond the glyph stream
```
